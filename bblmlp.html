What it is

BBLMLP is a machine learning and data engineering project I built, using baseball as the domain for practicing the parts of ML that are easy to get wrong: feature pipelines, leakage-safe validation and probability calibration. It ingests MLB data from 2021 to 2026 into a DuckDB warehouse, builds point-in-time features, trains a tuned Elo baseline and a stacked LightGBM, and evaluates both walk-forward.

The data

  • MLB StatsAPI for schedules, results, lineups and umpire crews.
  • Statcast pitch-level data through pybaseball, plus FanGraphs season tables, standings and the Chadwick player-id crosswalk.
  • Open-Meteo weather, with the wind resolved against each park's orientation.
  • One DuckDB warehouse. Rolling features are DuckDB window functions over game-level rollups for teams, starters, bullpens, batters, lineups and umpires. Every rate has an empirical-Bayes shrunk sibling whose priors are fit by method of moments.
  • A row-count gate on the training matrix: 13,952 rows, one per decided competitive game from 2021 to 2026, matched against a direct count of games season by season.

Leakage controls

Every feature is an as-of value, and the code and the tests enforce it rather than a convention.

  • Each rolling window ends one row before the game it describes, so a game's own statistics never enter its own features.
  • Tests perturb a game's own statistics and assert that its feature row does not move.
  • The splitters have no shuffle or random-state option, and a test asserts the API cannot grow one. Every training date comes strictly before every test date.
  • The probable-pitcher lookup returns the latest row strictly before the game date. A pitcher whose only row is that game gets nothing, never his own line.
  • Elo probabilities use only earlier games, so stacking Elo into the model does not leak.
  • Train/serve parity. One matrix-assembly function serves both paths: serving appends a placeholder row for the scheduled game and runs the same window code. Of 528 sampled games on single-game days, 524 reproduce every non-lineup feature on the serving path to within 1.4e-14, and the residuals (opening-day rest days, doubleheader game 2, posted lineups) are named, not hidden.

Models

  • A tuned Elo baseline. Elo's usual k = 20 is a constant borrowed from chess and never measured on baseball. Tuned on 2021 to 2023 (k = 8, season regression 0.5) and scored once on 2024 to 2026, it is worth +0.00362 Brier over k = 20 (paired t = +7.72).
  • A stacked LightGBM. The Elo probability goes in as a feature beside the rolling team, starter, bullpen, batter and lineup features, and the booster is early-stopped on its own slice of the training window.
  • Tree size chosen by monotonicity, where Brier could not decide. Brier could not separate 7, 15 and 31 leaves. PDP monotonicity ran 1.000, 1.000, 0.923 and 0.808 at 7, 15, 31 and 63 leaves, and at 31 the model had learned that a bullpen walking more batters helps its own team. The configured model uses 7.
  • Features earn their place. Five candidate groups (umpire, starter and bullpen xwOBA, handedness, fatigue) are worth −0.00008 Brier together (SE 0.00027, t = −0.31). Only fatigue stays on.
  • A plate-appearance outcome layer for simulation. 1,066,558 at-bats, 1,065,987 terminal events and 1,057,926 qualifying plate appearances, kept as three distinct counts, feeding base-out transitions, park factors and shrunk multinomial outcome rates. Its runs reconciliation build gate holds at 0 absolute error over 14,142 games. One finding it pins: Coors Field is the league's top hit park, not its top home-run park (2024 factors: hits rank 1 of 31, singles 1, strikeouts 31, home runs 12).

Evaluation

  • Season-aligned walk-forward folds. Each test fold is one whole season, trained on every season before it, so a three-game series can never straddle a split. Test seasons run 2022 to 2026.
  • Three disjoint, time-ordered slices inside each training window: fit (70%), early stopping (15%) and calibration (15%, the most recent).
  • A 16-cell matrix, every cell reported: raw or shrunk features, all seasons or 2023 onward (the rule-change era), Elo stacked or not, isotonic calibration or not. Four naive baselines (coin flip, always home, base rate, Elo) sit beside every run.
  • Metrics: Brier for selection, plus log loss, expected calibration error (ECE), the worst reliability bin and reliability diagrams. Accuracy is reported, never the objective. Comparisons are paired on identical games, with Bonferroni corrections when several tests run at once.
  • A pre-registered calibration gate. Isotonic calibration ships only if pooled Brier and ECE both improve, the same holds in at least 4 of the 5 season folds, and no single fold degrades by more than 0.005 Brier or 0.010 ECE. A fold with fewer than 1,000 calibration rows does not fit it at all, and the fold requirement scales down with it: the 2022 and 2023 folds were too small, so all 3 fittable folds had to improve. Measured: pooled ΔBrier +0.00102, ΔECE +0.00581, and 0 of 3 fittable folds improve. Isotonic does not ship, the configured model is the uncalibrated booster, and the gate re-runs on every evaluation.

The honest result

The stacked LightGBM ties a tuned two-constant Elo on Brier. That tie is the finding, recorded as the result of the model cycle (decision A1, 2026-10-15), instead of re-running the search until a model looks good. The model's earlier margin over Elo (+0.00376) was a margin over an untuned baseline: nothing about the model got worse, the yardstick got honest.

A leak caught in its own evaluation

The model is also scored against an external probability benchmark, and a first comparison made it look far ahead of the model. It was a leak, not skill: 429 of 7,776 captured home-side rows (5.5%) were taken after first pitch, and game times stored in UTC joined against local capture times made the obvious cutoff seven hours wrong, in the direction that lets in-game rows through. On the same 180 games with pregame rows only, its Brier went from 0.14861 to 0.24448, against the model's 0.24656. The evaluation now raises an error on any post-first-pitch row, and the honest comparison is a statistical tie (324 games, paired t = −0.37).

Engineering

  • About 17.2k lines of Python across 74 modules in src/, and about 19.2k lines of tests.
  • 1,282 tests collected, all hermetic: no test reads the warehouse or the network. GitHub Actions runs pytest and ruff (errors only) on pull requests and pushes to main, from a frozen uv lockfile.
  • Gates on real data run before merge. Checks that need the full warehouse (train/serve parity, the runs reconciliation, the matrix row count) run locally, and their measured numbers are written into the design spec.
  • A Typer CLI and pydantic settings over one DuckDB file. Tuned settings carry the measurement that chose them as inline comments.
  • A scheduled daily chain keeps schedules, lineups, umpire crews, features, projections and weather current during the season. After a stalled Statcast fetch hung it for 5.5 hours, every step got a timeout: a failure is logged and the whole chain retries the next day, and the regression test drives the default runner rather than an injected one. A timezone guard stops the job before it writes anything if the host is not in the zone its stored timestamps assume.

What is next

  • The game simulator. A Monte Carlo and Markov chain game simulator on top of the plate-appearance layer. It is designed and not built.
  • A run-environment model. Umpire features tie on the winner model for a structural reason (one strike zone for both clubs). Their most promising use is a total-runs model, which does not exist yet.
  • Better priors. A DerSimonian-Laird prior fit for the batter grain, and a Dirichlet successor for the plate-appearance rates that ships only if it wins held-out multinomial log loss.
